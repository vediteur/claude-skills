# 컴포넌트별 라이팅 규칙

글자 수는 **공백 포함 한국어 기준**이며, 모바일 360~390px 폭에서 한 줄에 대략 18~22자가 들어간다는 가정이다. 프로젝트 디자인 시스템에 규칙이 있으면 그것이 우선한다.

공통 규칙
- 어미: "~해요"체 기본. 어색한 문장만 "~합니다"체. 한 화면 안에서 섞지 않는다.
- 마침표: 본문이 두 문장 이상일 때만 찍는다. 타이틀·버튼·토스트 한 문장에는 찍지 않는다.
- 숫자는 아라비아 숫자, 단위는 붙여 쓴다(3분, 8칸, 3,200P).
- 사용자 호칭은 프로젝트 규칙을 따르고, 규칙이 없으면 호칭을 생략한다("고객님의" → 생략).

---

## 1. 확인 다이얼로그 (Confirm / Alert)

구조: 타이틀(질문 또는 사건) + 본문(결과 한 줄) + 메인 버튼 + 보조 버튼

| 요소 | 제한 | 규칙 |
|---|---|---|
| 타이틀 | 20자 이내, 한 줄 | "안내/알림/확인" 금지. 사건이나 질문 그 자체. 질문형이면 "~할까요?" |
| 본문 | 40자 이내, 최대 2줄 | 버튼을 눌렀을 때 일어나는 결과만. 질문은 타이틀에서 한 번만 |
| 메인 버튼 | 6자 이내 | 행동 동사. 실수 방지가 목적이면 안전한 쪽, 사용자 결정 존중이 목적이면 요청한 행동 |
| 보조 버튼 | 6자 이내 | "취소"는 실제로 되돌리는 행위에만. 그 외엔 "돌아가기", "계속 이용하기", "닫기" |

버튼 짝 예시: 끝내기 / 계속하기 · 나가기 / 돌아가기 · 삭제하기 / 취소(진짜 삭제 취소일 때) · 탈퇴하기 / 계속 이용하기

파괴적 행동(삭제·탈퇴·해지)일 때
- 본문에 **무엇이 사라지는지 2~3개 구체 명사**로 쓴다("주문 내역, 포인트, 저장한 글").
- "되돌릴 수 없어요"는 사실 고지로 허용. "영구 삭제", "다시는" 같은 공포 강조는 금지.
- 되돌릴 방법이 있으면 그것을 쓴다("30일 안에 다시 로그인하면 복구돼요").

흔한 실수(Before로 쓰기 좋은 안티패턴)
> 안내 / 정말 ○○하시겠습니까? ○○ 시 모든 데이터가 삭제되며 복구가 불가능합니다. 계속하시겠습니까? / [취소] [확인]

→ 빈 타이틀, 질문 2회, 극존칭, 한자어, "취소/확인"이 타이틀과 호응 안 됨, 결과 비구체.

## 2. 토스트 / 스낵바

| 요소 | 제한 | 규칙 |
|---|---|---|
| 본문 | 20자 이내, 한 줄 | 결과 완료형("저장됐어요", "복사했어요"). 설명·이유 없음 |
| 액션(선택) | 4자 이내 | 되돌리기, 보기, 다시 시도 |

- 성공 토스트에 "성공적으로", "정상적으로" 넣지 않는다 — 됐으면 됐다고만.
- 사라지는 컴포넌트이므로 반드시 알아야 할 정보(금액 출금, 삭제)를 토스트에만 두지 않는다.

흔한 실수: "요청이 성공적으로 처리되었습니다." → "저장됐어요"

## 3. 에러 메시지 (인라인 · 전체 화면)

구조: **무슨 일인지** → **그래서 무엇을 하면 되는지**. 원인 설명은 사용자가 고칠 수 있을 때만.

| 종류 | 제한 | 규칙 |
|---|---|---|
| 폼 인라인 에러 | 25자 이내 | 해당 필드 바로 아래. 무엇을 고칠지 구체적으로("8자 이상 입력해주세요") |
| 전체 화면 에러 | 타이틀 15자 + 본문 40자 + 버튼 | 시스템 탓이면 사과 한 번, 사용자 탓으로 돌리는 어감 금지 |

- 사용자를 주어로 한 부정("잘못 입력하셨습니다") 대신 해야 할 일("이메일 형식을 확인해주세요").
- 에러 코드·기술 용어(timeout, 500, invalid)는 사용자 문구에 노출하지 않는다. 필요하면 "문의 시 코드: E-1042"처럼 뒤에 작게.
- 재시도가 가능하면 버튼으로 준다("다시 시도"). 불가능하면 다음 경로를 준다("고객센터 문의").

흔한 실수: "오류가 발생했습니다. 다시 시도해주세요." → 타이틀 "연결이 끊겼어요" / 본문 "인터넷 연결을 확인하고 다시 시도해주세요" / 버튼 "다시 시도"

## 4. 푸시 알림 · 문자 · 카카오 알림톡

| 요소 | 제한 | 규칙 |
|---|---|---|
| 푸시 타이틀 | 20자 이내 | 사건 또는 혜택을 숫자와 함께("미션 4개가 나왔어요") |
| 푸시 본문 | 40자 이내 | 잠금 화면에서 앞 40자만 보인다고 가정. 핵심을 앞으로 |
| 문자 | 앞 20자에 핵심 | "(광고)" 등 필수 표기는 규정 위치에, 본문 첫 줄은 사용자에게 필요한 정보 |
| 알림톡 | 정보형 톤 | 광고처럼 읽히면 차단·신고로 이어진다. 기능·정보·뉴스처럼 |

- 개인화 변수({이름}, {포인트})는 값이 없을 때의 폴백 문장을 함께 만든다. 빈 자리("님, 안녕하세요")는 신뢰를 깨뜨린다.
- 시점 맥락을 맞춘다. 점심시간에 "잠시 쉬어가요"처럼 상황과 어긋나는 감성 카피는 당황만 준다.
- 제목만 보고 무엇을 하라는 건지 알 수 없는 카피("망설이지 마세요")는 본문까지 읽히지 않는다.
- 광고 목적이어도 "받을 수 있는 혜택 확인하기"보다 "이달의 혜택 도착"처럼 정보형으로.

흔한 실수: "{닉네임}님, 망설이지 마세요! 지금 바로 확인하세요" → "새 쿠폰 1장이 도착했어요 / 오늘 자정까지 쓸 수 있어요"

## 5. 빈 화면 (Empty State)

구조: 상황 한 줄 + (선택) 다음 행동 버튼

| 요소 | 제한 | 규칙 |
|---|---|---|
| 타이틀 | 20자 이내 | "데이터가 없습니다" 대신 사용자 관점 사건("아직 저장한 글이 없어요") |
| 본문 | 30자 이내 | 여기서 무엇을 할 수 있는지 |
| 버튼 | 8자 이내 | 첫 행동으로 바로 연결("글 둘러보기") |

- 사용자 잘못처럼 읽히는 표현("아직 아무것도 안 하셨네요") 금지.
- 검색 결과 없음은 검색어를 반복해 보여주고 대안을 제시("'스위블'에 맞는 결과가 없어요 / 다른 검색어로 찾아보세요").

## 6. 버튼 · 링크 라벨

- **동사로 끝낸다**: 확인·OK·예/아니오 대신 행동("저장하기", "보내기", "다음").
- 6~8자 이내. 두 단어를 넘기지 않는다.
- 버튼을 누른 뒤 나오는 화면을 라벨이 예고해야 한다. "혜택 받기"를 눌렀는데 설문이 나오면 실패.
- 하나의 화면에서 같은 행동은 같은 라벨. "삭제"와 "지우기"를 섞지 않는다.
- "지금", "바로", "무료로" 같은 재촉 부사는 기본적으로 뺀다. 넣어도 사실일 때만.

## 7. 폼 라벨 · 플레이스홀더 · 도움말

| 요소 | 규칙 |
|---|---|
| 라벨 | 명사형, 8자 이내("휴대폰 번호"). 필수 표시는 라벨 옆에 일관되게 |
| 플레이스홀더 | 입력 예시 또는 형식("010-0000-0000"). 라벨을 대신하지 않는다(입력하면 사라지므로) |
| 도움말 | 25자 이내. 왜 필요한지 또는 형식 조건. 에러 전에 미리 보여주면 에러가 줄어든다 |

- 내부 용어("요청서", "시안 확정") 대신 사용자가 하는 일로 라벨을 붙인다.

## 8. 온보딩 · 랜딩 첫 화면

- 첫 화면에는 브랜드명·이벤트명·자사 용어를 쓰지 않는다. 사용자는 그것이 무엇인지 아직 모른다.
- 헤드라인은 사용자가 얻는 것 하나만("3분 만에 보험 가입"). 기능 나열 금지.
- 후킹이 필요하면 `content-hooks.md`의 5조건 중 2개 이상.
